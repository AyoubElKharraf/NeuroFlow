2. ETAPE 1 : AJOUT DES DEPENDANCES MAVEN
===============================================================================
OÙ :
Fichier : NeuroFlow/neuroflow-backend/pom.xml

QUOI :
Ajout de deux dépendances Flyway dans la section <dependencies> :
- org.flywaydb:flyway-core
- org.flywaydb:flyway-database-postgresql

POURQUOI :
Depuis Spring Boot 3 / Flyway 10+, le moteur Flyway a été modularisé. 
Le support spécifique pour PostgreSQL n'est plus inclus nativement dans flyway-core.
Il est obligatoire d'ajouter flyway-database-postgresql pour permettre la 
connexion et l'exécution des scripts sur PostgreSQL.

EXTRAIT MODIFIE DANS pom.xml :
-------------------------------------------------------------------------------
        <!-- Persistence (PostgreSQL) -->
        <dependency>
            <groupId>org.springframework.boot</groupId>
            <artifactId>spring-boot-starter-data-jpa</artifactId>
        </dependency>
        <dependency>
            <groupId>org.postgresql</groupId>
            <artifactId>postgresql</artifactId>
            <scope>runtime</scope>
        </dependency>

        <!-- Flyway Database Migration -->
        <dependency>
            <groupId>org.flywaydb</groupId>
            <artifactId>flyway-core</artifactId>
        </dependency>
        <dependency>
            <groupId>org.flywaydb</groupId>
            <artifactId>flyway-database-postgresql</artifactId>
        </dependency>
-------------------------------------------------------------------------------

3. ETAPE 2 : CONFIGURATION DU SCHEMA ET DE FLYWAY
===============================================================================
OÙ :
Fichier : NeuroFlow/neuroflow-backend/src/main/resources/application.yml

QUOI :
1. Remplacement de "spring.jpa.hibernate.ddl-auto: update" par :
   "spring.jpa.hibernate.ddl-auto: ${SPRING_JPA_HIBERNATE_DDL_AUTO:validate}"
2. Ajout du bloc de configuration "spring.flyway" :
   - enabled: ${FLYWAY_ENABLED:true}
   - baseline-on-migrate: ${FLYWAY_BASELINE_ON_MIGRATE:true}
   - locations: ${FLYWAY_LOCATIONS:classpath:db/migration}

POURQUOI :
1. Hibernate ddl-auto: validate :
   En production et en architecture propre, confier la création/mise à jour du 
   schéma à Hibernate (ddl-auto: update) est dangereux (pas de rollback possible, 
   pas d'historique). Le mode "validate" force Hibernate à vérifier au démarrage 
   que les entités Java correspondent strictement aux tables en base, sans y toucher.
2. baseline-on-migrate: true :
   Lorsque Flyway s'exécute sur une base existante non vierge (par exemple une base 
   créée par un script d'initialisation Docker ou un ancien schéma), Flyway refuse 
   par défaut de migrer pour ne pas corrompre les données. L'option 
   "baseline-on-migrate: true" indique à Flyway d'enregistrer l'état actuel de la 
   base comme référence (Baseline v1) et de poursuivre sereinement.

EXTRAIT DANS application.yml :
-------------------------------------------------------------------------------
  jpa:
    hibernate:
      ddl-auto: ${SPRING_JPA_HIBERNATE_DDL_AUTO:validate}
    open-in-view: false
    properties:
      hibernate:
        jdbc:
          time_zone: UTC
        format_sql: true
    show-sql: false

  flyway:
    enabled: ${FLYWAY_ENABLED:true}
    baseline-on-migrate: ${FLYWAY_BASELINE_ON_MIGRATE:true}
    locations: ${FLYWAY_LOCATIONS:classpath:db/migration}
-------------------------------------------------------------------------------

4. ETAPE 3 : CREATION DU SCRIPT DDL INITIAL (V1)
===============================================================================
OÙ :
Fichier : NeuroFlow/neuroflow-backend/src/main/resources/db/migration/V1__init_schema.sql

QUOI :
Création du script SQL initial contenant la table "app_users", ses contraintes 
et ses index.

POURQUOI :
Ce script reflète exactement l'unique entité JPA du projet :
com.neuroflow.backend.domain.AppUser
- Clé primaire auto-incrémentée (BIGSERIAL / IDENTITY)
- username : VARCHAR(64), non nul, unique
- password_hash : VARCHAR(100), non nul
- roles : VARCHAR(128), non nul
- enabled : BOOLEAN, non nul avec valeur par défaut TRUE
- Index idx_app_users_username pour accélérer les requêtes d'authentification.

CONTENU EXACT DU FICHIER V1__init_schema.sql :
-------------------------------------------------------------------------------
-- =============================================================================
-- Migration V1: Initial schema for NeuroFlow PostgreSQL database
-- Corresponds to JPA Entity: com.neuroflow.backend.domain.AppUser
-- =============================================================================

CREATE TABLE IF NOT EXISTS app_users (
    id            BIGSERIAL PRIMARY KEY,
    username      VARCHAR(64) NOT NULL UNIQUE,
    password_hash VARCHAR(100) NOT NULL,
    roles         VARCHAR(128) NOT NULL,
    enabled       BOOLEAN NOT NULL DEFAULT TRUE
);

-- Index for optimized lookups on username
CREATE INDEX IF NOT EXISTS idx_app_users_username ON app_users (username);

6. ANALYSE ET RESOLUTION DES ERREURS RENCONTREES
===============================================================================

-------------------------------------------------------------------------------
ERREUR 1 : "cd : Impossible de trouver le chemin d'accès ...\NeuroFlow\NeuroFlow\neuroflow-backend"
-------------------------------------------------------------------------------
CAUSE :
Le terminal PowerShell se trouvait déjà dans le dossier "...\Project 1 - FlyWay\NeuroFlow".
Taper "cd NeuroFlow/neuroflow-backend" a provoqué une tentative d'accès à un double 
dossier inexistant.
SOLUTION :
Taper simplement : cd neuroflow-backend

-------------------------------------------------------------------------------
ERREUR 2 : "ClassNotFoundException: com.neuroflow.backend.NeuroFlowBackendApplication" lors de "mvn spring-boot:run"
-------------------------------------------------------------------------------
CAUSE :
1. Bug Windows / Java lié aux chemins avec accents : Le chemin du projet contient 
   "Génie Logiciel" (avec un "é"). Le plugin Maven spring-boot génère un fichier 
   d'arguments temporaire (@argfile) dont l'encodage sous Windows corrompt le "é", 
   rendant le dossier des classes introuvable par java.exe.
2. Conflit de port : Le conteneur Docker "neuroflow-backend" tournait déjà sur 
   le port 8080.
SOLUTION :
L'application s'exécute dans Docker via docker compose. Si une exécution locale 
est nécessaire, exécuter directement : java -jar target/neuroflow-backend-0.1.0-SNAPSHOT.jar 
(en arrêtant au préalable le conteneur backend).

-------------------------------------------------------------------------------
ERREUR 3 : "FATAL: role "postgres" does not exist"
-------------------------------------------------------------------------------
CAUSE :
La commande exécutée était :
docker exec -it neuroflow-postgres psql -U postgres -d neuroflow -c "..."
Or dans ce projet, l'utilisateur PostgreSQL est "neuroflow" et la base est "neuroflow_db".
SOLUTION :
docker exec -it neuroflow-postgres psql -U neuroflow -d neuroflow_db -c "..."

-------------------------------------------------------------------------------
ERREUR 4 : "no such service: neuroflow-backend"
-------------------------------------------------------------------------------
CAUSE :
La commande exécutée était :
docker compose up -d --build neuroflow-backend
Or dans "docker-compose.yml", le bloc services déclare le service sous le nom 
"backend:" ("neuroflow-backend" est uniquement la propriété "container_name").
SOLUTION :
docker compose up -d --build backend
